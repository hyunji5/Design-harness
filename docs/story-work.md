# 디자인 작업 흐름 (AI 없이 손으로 했던 방식)

이 문서는 "내가 실제로 어떻게 했는지"를 기록한다. "무엇을 위한 일인지"는 [story-service.md](story-service.md)에 따로 있다.

## 작업 문장

1. 나는 uibowl에서 경쟁 서비스의 행사 캘린더·입점 신청·이벤트 게임 화면을 모아 **레퍼런스 보드**를 만든다.
2. 나는 레퍼런스 보드를 화면별로 분석해 우리 서비스에 가져올 패턴을 골라 **레퍼런스 분석 노트**를 쓴다.
3. 나는 분석 노트를 바탕으로 5개 화면(행사 달력, 행사 상세, 가게 신청 심사, 게임 설정, 손님용 휴대폰 화면)의 **화면 설계서**를 구체화한다.
4. 나는 Figma에 레퍼런스와 화면 설계서를 반영한 **키 스크린 시안** 2~3개를 390×844 사이즈로 그린다.
5. 나는 내부 관계자들과 시안을 협의해 **확정 컨셉 시안**을 정한다.
6. 나는 확정 시안을 기준으로 **디자인 토큰**과 **컴포넌트**를 만들고, 나머지 **화면 디자인**을 완성한다.
7. 나는 완성된 화면 디자인의 토큰·컴포넌트가 우리 디자인 가이드를 어겼는지 검토해 **가이드 검토 결과**를 남긴다.

## 산출물 · 게이트 · 에이전트 경계

| # | 산출물 | 게이트 (멈칫한 지점) | 에이전트 경계 (넘김) |
|---|---|---|---|
| 1 | 레퍼런스 보드 | 몇 개를 모아야 충분한지 기준이 없어서 계속 더 찾게 된다. | 🔧 나 → uibowl |
| 2 | 레퍼런스 분석 노트 | 가져올 것과 버릴 것을 감으로 고르고 있어서 맞는 판단인지 확신이 없다. | 없음 (혼자 끝냄) |
| 3 | 화면 설계서 (5개 화면) | PRD 요구사항(예: 날짜 변경 시 영향받는 일 전부 표시)이 설계서에 빠짐없이 들어갔는지 대조하느라 오래 걸린다. | 없음 (혼자 끝냄) |
| 4 | 키 스크린 시안 2~3개 (390×844) | 5개 화면 중 어떤 걸 키 스크린으로 골라야 컨셉이 잘 보일지 고민된다. | 🔧 나 → Figma |
| 5 | 확정 컨셉 시안 | **(가장 큼)** 의견이 갈릴 때 누가 최종 결정하는지 분명하지 않다. | 👥 나 → 내부 관계자(기획·개발·마케팅). 결정이 나 혼자에게서 여러 사람으로 넘어간다. |
| 6 | 디자인 토큰, 컴포넌트, 화면 디자인 | 토큰을 먼저 확정할지, 화면을 그리면서 토큰을 뽑을지 순서가 매번 흔들린다. | 🔧 나 → Figma |
| 7 | 가이드 검토 결과 | 위반을 찾았을 때 바로 고칠지, 예외로 남길지 판단 기준이 없다. | 👥 나 → 개발팀 (화면 디자인·디자인 토큰·컴포넌트 + 가이드 검토 결과) |

## 메모

- 6번은 실제로 한 그대로 한 단계로 기록한다. 단계 분할은 R3(파이프라인)에서 정한다.
